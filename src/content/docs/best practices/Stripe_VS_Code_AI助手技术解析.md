## Stripe 新版 VS Code AI 助手技术解析

> 原文发表于 2025 年 3 月 18 日，作者 Mathew Varughese（Stripe 软件工程师）

Stripe 的 `docs.stripe.com` 原始文本内容超过 130 MB（作为对比，我大学时的操作系统教材只有 7 MB 的 PDF），并且每周更新数百次。虽然大语言模型在预训练中包含 Stripe 的知识，但它们几乎会瞬间过时，而且偶尔会产生不正确的信息。支付集成非常复杂，Stripe 也提供了大量可定制性。

正因如此，我们在 VS Code 扩展中构建了一个 Stripe AI 助手，它通过搜索相关的 Stripe 知识（如 API 参考条目、集成指南、代码示例和开发者 Discord 讨论线程）来回答你的问题。相比单独使用原始 LLM，这提高了准确性，并且可以根据你的 Stripe 账户提供个性化回复。

### 使用方式

访问 https://ai.stripe.com/vscode 即可自动安装并打开 Stripe AI 助手。

该扩展也可在 VS Marketplace 获取。我们建议同时安装 Stripe CLI 以启用更多功能（流式 Webhook 事件、个性化 AI 回复等）。

GitHub Copilot 用户可以在聊天中输入 `@stripe` 开始使用。如果不使用 Copilot，扩展也提供了独立的聊天 UI。

助手会调用我们的后端来获取最新的 Stripe 文档。这减少了"幻觉"问题——即 LLM 产生事实上不正确的输出。扩展还会自动插入你的 API 密钥，让你可以快速测试能直接运行的代码片段。

运行助手生成的定制代码，我们可以得到一个可用的支付链接：

```python
import stripe

stripe.api_key = "rk_test_..."

product = stripe.Product.create(
    name="Original Abstract Painting",
    description="24x36 inch acrylic on canvas",
    images=["https://example.com/artwork-image.jpg"],
)

price = stripe.Price.create(
    product=product.id, unit_amount=50000, currency="usd"  # $50.00
)

payment_link = stripe.PaymentLink.create(
    line_items=[{"price": price.id, "quantity": 1}]
)

print(f"Share this payment link: {payment_link.url}")
```

### 从文档引导的集成流程

我们还在文档中推出了"在 VS Code 中打开"按钮。我们从集成快速入门指南开始。这将深度链接到 VS Code 扩展，并在你的编辑器中直接引导你完成特定集成。它拥有相同的 AI 辅助工具，因此你可以在集成过程中的任何时候提问，并获得针对你代码库的特定回答。

### 技术架构

为了解决 LLM 幻觉问题，我们使用检索增强生成（RAG）来选取正确的 Stripe 知识片段，并将其放入发送给 LLM 的 prompt 中。以下是提问时发生的步骤：

1. **分类器**：我们将查询分类为不同的类别（API 参考、文档、编码帮助等）。这也有助于防止对抗性或不相关的问题，并通过扩展查询来提高检索效果。

2. **检索**：我们持续调整索引和查询设置以改进搜索。总体而言，我们结合了基于 BM25 的关键词搜索和 K 近邻嵌入搜索来检索相关文档片段。

3. **重排序**：以问题"Connect 集成的主要组件有哪些？"为例，朴素搜索可能会返回"Embedded Connect 组件入门"文档，但更好的选择是我们更通用的 Connect 概览指南。重排序是在检索后重新排列搜索结果的过程；我们使用页面流量和其他因素来调整结果顺序。

4. **Prompt 构建**：我们结合相关文档来源、代码片段示例、用户代码和用户问题构建 prompt，将完整 prompt 发送给 LLM（目前使用 Claude Sonnet），然后将响应流式传输回 VS Code 助手。

为了确保助手保持最新状态，我们有一个夜间的 Temporal 工作流，对数千份集成指南、API 参考条目、代码示例和总结的开发者 Discord 线程进行分块和嵌入。由于文档可能太长，LLM 无法轻松消化，我们通过将文档拆分为更小的部分来"分块"。然后将这些片段的语义含义编码为嵌入向量。我们作为检索集的一部分对这些嵌入进行搜索。

对于 VS Code 扩展聊天 UI，我们与微软合作，成为新聊天扩展框架的首批用户之一。借助该框架，任何 VS Code 扩展都可以贡献一个"@可提及的代理"，使 GitHub Copilot 更强大。

### 评估体系

在使用 AI 时衡量成功至关重要。由于 LLM 是非确定性的，我们需要仔细客观地评估回复质量。每个用户的问题（经过 scrub 以移除任何个人身份信息）和生成的响应都会记录到我们的 LLM 评估工具中。然后我们可以比较不同批次的问题及其响应。

#### 第一步：构建数据集

我们构建了一个"黄金"数据集，包含用户问题以及我们确定的回答这些问题的最佳文档。但为了充分测试我们的 RAG 系统，我们需要更多数据。我们用一个合成数据集扩充了这个黄金数据集——使用 LLM 生成与每份 Stripe 文档相关的用户可能提出的问题。我们手动检查了生成的问题，并删除了任何不合理的问题。完成这些后，我们现在有数千个问题及其对应的预期 URL。

#### 第二步：衡量

当用户问"Checkout 使用哪个客户地址来计算税费？"时，回复应该使用 `docs.stripe.com/payments/checkout/taxes` 文档。正确性最简单的衡量标准是：检索步骤是否选对了文档？

然而，检索引擎返回的是多个文档的有序列表，所以我们可以更精细地衡量正确性。我们使用平均倒数排名（MRR）来测试我们的相关性评分和重排序的有效性。如果我们检索到一个文档但它排在第二位，该文档的得分会比排在第十五位时更高。MRR 计算为 1 / 位置，所以如果正确文档在第二位被检索到，MRR 将为 0.5，第三位为 0.33，第四位为 0.25，依此类推。对所有问题的这些倒数排名取平均值，就得到了整体正确性衡量。

#### 第三步：改进

有了评估系统，我们可以对检索行为形成假设并相应地调整它。例如，我们注意到仅靠语义嵌入搜索在选择 API 参考的相关部分方面表现不佳。我们开始使用结合传统关键词搜索和语义嵌入搜索的"混合"搜索，并看到了准确率分数的提升。另一个例子是，我们发现许多类似"如何构建支付应用"的问题由于包含 Stripe Apps 文档而 MRR 较低。我们改进了分类和重排序策略来修复这个问题，并看到了改进。

这个评估套件每晚运行，以确保质量没有回退。目前，在我们的测试合成数据集上，我们包含最佳来源的概率约为 91.11%，MRR 约为 78%。我们还手动评估实时用户日志（包括生成回复的实际文本以及来源准确性）。为了帮助扩展这些手动评估，我们还构建了一个自动化的 LLM-as-a-Judge 系统。该系统阅读用户线程并对我们的 AI 回复进行评分（此回复是否帮助回答了用户的问题？是否有用？）。我们通过将其分数与我们自己的分数进行比较，持续改进 LLM-as-a-Judge。这帮助我们在获得更多使用时扩展评估。

### 总结

借助 Stripe VS Code AI 助手，你可以快速集成 Stripe，在编辑器中直接提问。阅读 Stripe VS Code 扩展文档以了解更多信息。我们才刚刚开始——如果你有其他想法或建议，请在 Stripe Insiders 上分享。
